**Вердикт по шагу 0 — условный.**
* Разметка (транскрипты, вердикты по кадрам) — это выходы модели Alibaba. Использовать их как обучающие данные для **модели чтения по губам** формально попадает под 4.6 только если считать её продуктом, «конкурирующим» с сервисом и моделями Alibaba. Прямой конкуренции с Qwen (универсальные модели, ASR) здесь нет, но формулировка «相竞争的产品或服务» не определена, а чтение по губам для диктовки — рядом с их ASR (fun-asr, qwen-audio) как речевой продукт. Строить коммерцию на молчаливом толковании рискованно.
* **Самое безопасное:** использовать Alibaba для **фильтрации и сверки** (какие ролики брать, где GigaAM ошибается), а метки для обучения оставлять GigaAM/человеческие. Тогда выходы Alibaba в обучающие данные не попадают.
* Если нужны выходы Alibaba в обучении (особенно для продажи) — получить **письменное разрешение** Alibaba по 4.6 (контакты в соглашении), до масштабирования.
* Синтетика из TTS/генераторов видео (раздел «1c») — те же выходы платформы; для неё действуют 4.6 и 7.5 так же.

### Шаг 2. «Учитель»: стоит ли того, только если лучше нашей модели (62,8% WER)

**Нет.** Нулевой запуск: 94–102% WER (раздел 1). Дообучение: видео-SFT возможно только на Qwen3.5+ (4B/9B/27B…), `fps ≤ 10`, 224 px; задание на 187 клипов выполнено,
но деплой этой модели на ключе недоступен, WER не измерен, а кривая отложенных клипов не улучшилась (раздел 2). Даже в оптимистичном случае 27B-учитель на нескольких сотнях клипов не приблизится к 62,8%.
Для реального учителя нужны десятки тысяч клипов, обучаемый ViT и деплой, чего ключ не даёт.

### Шаг 3. Можно ли скачать веса дообученной модели

**Нет, ни полные веса, ни LoRA-адаптеры.** Слова документации (help.aliyun.com, регион Пекин, проверено по исходному HTML):
* FAQ [«Fine-tune models in the console»](https://help.aliyun.com/en/model-studio/model-training-on-console): *«Can I download a model fine-tuned on Alibaba Cloud Model Studio for local deployment?»* — *«Models fine-tuned on Alibaba Cloud Model Studio cannot be exported. They can only be tested and invoked after deployment on Model Studio.»*
* Там же и в [обзоре](https://help.aliyun.com/en/model-studio/model-training-overview): *«Exported parameter snapshots are saved in cloud storage and cannot be accessed or downloaded.»* (экспорт нужен только для деплоя в самом Model Studio).
* Адаптеры LoRA в документации упомянуты только как способ обучения («efficient SFT»), выгрузки не описано. API экспорта (`GET /fine-tunes/{job}/export/{checkpoint}`) тоже создаёт модель внутри платформы, не скачивание (проверено на запущенном задании: «Checkpoint has already been exported successfully»).

### Рекомендация одним абзацем

Сегодня работают шаги (a) «метки речи» и (b) «проверка кадров» как **вспомогательные**: fun-asr-flash ≈ ¥0,79 за час аудио и ≈ 840 ч в сутки на ключ даёт второе независимое мнение к GigaAM, а Qwen3-VL-Plus по трём кадрам за ≈¥0,0013 за видео находит нормальные ролики, которые Haar отбрасывает; их стоит переносить на ключ сразу, но использовать как **фильтр и сверку**, не как источник обучающих меток. Учитель (шаг 2) и скачиваемая модель (шаг 3) не работают: нулевое чтение по губам 94–102% WER, дообучение видео-моделей ограничено 10 к/с и без вызываемого деплоя, веса дообученных моделей Alibaba не отдаёт. Условие, которое решает юридически, — пункт 4.6: пока нет письменного разрешения Alibaba или юридического заключения, выходы платформы (метки, синтетические видео и речь) не стоит класть в обучающий корпус модели, которую предполагается продавать; учить её надо на своих GPU на открытой Apache-2.0-основе или на MultiVSR-подобной архитектуре с собственной лицензией.

## 1. Чтение по губам без обучения

**Набор.** 50 клипов из `data/public_pod` (`results/dashscope/clips_pool100.json`, первые 50): по одному клипу на ролик, 2,5–8 с,
не меньше 4 слов, источник YouTube; до 24 клипов с одного канала. Эталон — текст GigaAM из `.txt`.
Это лицевые кропы 224×224 из роликов в 360p, без звуковой дорожки (проверено `ffprobe`). Тексты не пересекаются
с обучающим набором раздела 2 (ролики разные), но каналы те же — в корпусе их всего четыре, отложить целый канал не из чего.
Погрешность WER на 50 клипах около ±5–8 пунктов, поэтому различия в 1–3 пункта между строками ниже ничего не значат.

## 2. Дообучение на видео (Model Studio)

### Что разрешает документация и API

Источники: help.aliyun.com/en/model-studio — `model-training-overview`, `text-generation-tuning-data-upload-rules`,
`fine-tuning-api-guide`, `create-fine-tuning-job-api`, `model-training-and-deployment-billing`, `create-deployment-api`.
Всё только для региона Пекин (ключ из конфига пекинский).

* **Видео в SFT-данных — только Qwen3.5 и новее** (3.5-4B/9B/27B, 3.6, 3.8-27B…). Qwen3-VL-8B/4B и Qwen2.5-VL принимают только картинки.
* **Формат.** Zip ≤2 ГБ с `data.jsonl` в корне и видеофайлами рядом (только ASCII, буквы/цифры/`_`/`-`, имя без расширения ≤120 знаков,
  имена уникальны). Строка: `{"messages":[{"role":"user","content":[{"video":"x.mp4","fps":10.0},{"text":"..."}]},{"role":"assistant","content":[{"text":"..."}]}]}`.
  Необязательно: `resized_width/height`, `video_start/video_end`. Через API zip загружается `POST /api/v1/files` (purpose=fine-tune), ≤300 МБ на файл.
* **`fps` в обучении ≤ 10** (диапазон 0,1–10). Клипы 25 к/с поэтому нужно **перетаймить** (здесь `setpts=2.5*PTS`, `-r 10`:
  все 132 кадра сохраняются, длительность ×2,5), иначе обучение увидит только 40% кадров.
* **Минимумы и потолки, найденные опытом, а не из документации:**
  * `batch_size` ∈ [64, 32768], выборка должна быть **строго больше** `batch_size` *после фильтра по длине* (иначе задание
    падает через 7–9 минут, без списания).
  * `max_length`: клип 224 px, 3–6 с в виде 10 к/с — **4,5–11,5 тыс. токенов** (в среднем 8,5 тыс.). При рекомендуемых 8192 часть
    выборки молча отбрасывается и получается «Insufficient number of valid training data». Нужно ставить 32768.
  * Одновременно идёт одно задание, остальные ждут в очереди. Из 54 мин задания само обучение заняло ≈ 25 мин, остальное — очередь, подготовка данных и экспорт.
  * Токенный тариф API-заданий только при `freeze_vit=true`; с обучаемым ViT — только консоль и «единицы обучения».
    А для чтения по губам именно визуальная часть, скорее всего, должна обучаться (см. ниже).
* **Цена обучения (за 1000 токенов):** Qwen3.5-4B ¥0,015; 9B ¥0,02; 27B и 3.8-27B ¥0,05. Токены = (токены данных) × эпохи.

### Можно ли вызвать дообученную модель — нет, на этом ключе

* Чекпоинт экспортирован в модель платформы. Вызов через `/compatible-mode/v1/chat/completions`
  → `model_not_found` (до деплоя модель не вызывается).
* `POST /api/v1/deployments` с `plan=lora` (оплата токенами): **404 «not found with plan lora»**. В прайсе токенного LoRA-деплоя есть
  Qwen3.5-27B и Qwen3-VL-8B (картинки), но не 4B/9B.
* С `plan=mu` (почасовая аренда): **403 «Service not activated: sfm_modelunits_public_cn»** — услуга не включена на аккаунте.
  Цены по прайсу: Qwen3.5-27B ¥47–51 в час (MU8/MU9 ×1), Qwen3.5-9B ¥108 в час.
* Итого единственный полностью токенный путь с видео — **Qwen3.5-27B + efficient_sft + `lora`-деплой**. Он не запускался:
  при тех же 7,5 млн токенов это ≈ ¥375 (≈ $52), 54+ мин, и по кривой выше результат, скорее всего, будет «около 95–100% WER».
  Чтобы закрыть вопрос точной цифрой, достаточно 2 эпох на 27B (≈ ¥150) и 50 тестовых клипов через `dashscope_probe/zeroshot.py`
  (нужно добавить вызов с `fps=10` и именем развёрнутой модели).
* Ограничения, не зависящие от цены: `fps ≤ 10`, шаг не меньше 64 клипов, а визуальная часть через токенный API заморожена.
  MultiVSR обучается на 25 к/с, по ~79 тыс. клипов и с обучаемой визуальной частью; сравнивать с ней задание на 187 клипов бессмысленно.

## 3. Проверка кадров через Qwen3-VL-Plus

Метод: 3 кадра YouTube (`i.ytimg.com/vi/<id>/hq1..3.jpg`, те же, что берёт сборщик), один запрос с тремя картинками, ответ JSON
(`faces_per_frame`, `close_up`, `reason`). 50 видео из `newdata/state.db`.

| Эталон | Состав | TP | FP | FN | TN | Точность |
|---|---|---:|---:|---:|---:|---:|
| s4_face (реальное видео, FaceMesh): прошли дальше / отклонены (face_frac, not_frontal, face_small) | 21 / 29 | 20 | 28 | 1 | 1 | **42%** |
| s1b_thumb (Haar по тем же миниатюрам): прошли / «no_face_thumbs» | 25 / 25 | 22 | 9 | 3 | 16 | **76%** |

* Модель почти всегда говорит «подходит». Её критерий «лицо ≥15% ширины, один человек, анфас» мягче, чем у сборщика:
  s4_face смотрит на 30 с видео, считает долю кадров с лицом и поворот головы, а три миниатюры этого не видят. Заменить s4_face нельзя.
* Против Haar по тем же кадрам: из 25 «no_face_thumbs» модель одобряет 9, в ответах «один человек, лицо ~30–40% ширины, анфас».
  Эти 9 видео не проверены глазами и не прошли через s4_face (запускать FaceMesh на маке нельзя) — вероятно, это упущенные Haar
  нормальные ролики (Haar тяжело работает с наклоном и тенью). Три отказа модели у «прошедших» — несколько людей или коллаж в одном из кадров, что разумно.
* Скорость и цена: ≈740 токенов на запрос, 3,3–3,5 с задержка, **≈12–13 запросов/с на один ключ при 24 потоках, ни одного 429** (суммарно по трём ключам 10,4 запр./с в первом тесте;
  предел не нащупан). Оценка запросов в сутки: при 12 запр./с на одном ключе ≈ 1 млн, то есть вся
  очередь `queue_diverse.txt` (37,5 тыс. строк) пройдёт примерно за час. Цена ≈ ¥0,0013 за видео, вся очередь ≈ ¥50.

## 4. Разметка речи на стороне Alibaba

Клипы `public_pod` беззвучные (лицевые кропы), поэтому звук нарезан заново из YouTube (`yt-dlp --download-sections`, без куки, 16 кГц моно;
`dashscope_probe/fetch_audio.py`). 49 из 50 нарезаны (в одном случае 403). Вызов — нативный
`POST /api/v1/services/aigc/multimodal-generation/generation`, `input_audio` в data-URI, `language_hints=["ru"]`
(compatible-mode для этих двух моделей не нужен и не проверялся).

| Модель | WER к GigaAM | CER | точное совпадение после нормализации | сек/клип | цена |
|---|---:|---:|---:|---:|---|
| fun-asr-flash-2026-06-15 | **5,1%** | **1,9%** | 30/49 | 2,4 | ¥0,00022/с = ¥0,79/ч |
| qwen-audio-3.0-asr-flash | 5,7% | 2,9% | 29/49 | 4,1 | ¥0,00022/с |
| fun-asr против qwen-audio между собой | 6,5% | — | 27/49 | — | — |

* Это согласие, а не точность: сам GigaAM ошибается. В 4 из 19 расхождений обе модели Alibaba одинаковы между собой и против GigaAM,
  и правы они: «день» вместо «деньги», «ничего нету» против «нет», «айти» против «ит», лишнее «а» на краю клипа. Остальное — границы клипа
  (нарезки со звуком могут сдвигаться на 0,1–0,2 с) и числа/стиль. Для сравнения: расхождение GigaAM с субтитрами YouTube — 4,4%.
* Знаки препинания и регистр в ответах есть, `metrics.normalize` их убирает.
* Пропускная способность: три ключа вместе, 16 потоков — 33 с аудио/с, 48 клипов за 8,7 с, без 429; **один ключ, 16 потоков — ≈35 с аудио/с, но 6–9% ответов 429** (повтор помогает), то есть ≈840 ч аудио в сутки на ключ.
  На 5000 ч это ≈ ¥4000 против бесплатного GigaAM на поде — выгода только в экономии GPU-времени и в независимом втором мнении.

## Что переносить на ключ

1. **Второй разметчик речи (fun-asr-flash)** по выборке клипов каждого канала: обнаруживать каналы, где GigaAM расходится с ним > 8–10% по словам
   (R14 сейчас сверяет с автосубтитрами YouTube; fun-asr независим от субтитров и от GigaAM). ≈ ¥0,8 за час, мак свободен.
   Метка «обе модели Alibaba против GigaAM» — кандидат на правку текста клипа.
2. **Сито по миниатюрам вместо Haar (`s1b_thumb`)** в `newdata/qd_work/faces.py` — Qwen3-VL-Plus по 3 кадрам, около ¥0,0013 за видео.
   Сначала на ~200 видео сравнить результат с реальным s4_face для тех, кого Haar отверг, чтобы подтвердить рост выхода.
   Оставить s4_face и синхронность на подах.
3. **Не переносить:** нулевое чтение по губам, дообучение видео-моделей (нет вызываемого деплоя, 10 к/с, кривая на 187 клипах не обобщается), а также
   вычисление признаков/обучение — оно дешевле на подах.
4. Текстовая правка гипотез MultiVSR через Qwen (`llm_rescore.py`) уже работает на ключе и остаётся там: это текстовая задача, а не чтение по губам.

## Предупреждения

* Потрачено на API: обучение ≈ ¥112 (по прайсу), нулевые запуски, проверка кадров и ASR — несколько юаней по прайсу токенов
  (самые тяжёлые — 18 тыс. токенов видео на замедленный клип и ~5,8 тыс. токенов размышления у Qwen3.8-Omni).
* Лимиты запросов не нащупаны: максимум 24 параллельных потока и ~10 запр./с без единой 429.
* Все WER на 50 клипах: ±5–8 пунктов (R13 в `RULES.md`).
