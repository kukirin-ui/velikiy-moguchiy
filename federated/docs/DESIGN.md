# Федеративное дообучение «Великого & Могучего»: архитектура

Статус: разделы 1–14 описывают протокол и эталонный сервер из `server/` для обучения на личных записях; этот режим
проверен только локально (сервер на localhost, обучение на крошечной модели-заменителе и дымовой прогон на реальных
формах LoRA MultiVSR), сервера для него нет. Раздел 15 — «Помочь обучить» на публичных роликах: сервер приёма на
Cloudflare Workers, агрегатор в GitHub Actions, хранение на Hugging Face; он работает. Всё, что ниже не помечено как
план, есть в коде; пометка *(план)* значит, что это описано, но кода пока нет.

## 1. Решение продукта и границы

- Установка, пользователь которой дал **отдельное согласие** (по умолчанию его нет, `client/consent.py`), обучает
  LoRA-адаптер **локально на своих данных** и отправляет на сервер только **обновление весов адаптера** (дельту). Без
  согласия клиент не скачивает модель, не обучает и не отправляет; решение проверяется в начале каждого прохода. Текст
  согласия: `AGREEMENT.md`.
- Модель: MultiVSR (трансформер ~279 млн параметров, веса заморожены), LoRA ранг 16 на проекциях q и v во всех 36
  вниманиях (энкодер 12, самовнимание декодера 12, кросс-внимание 12): 72 адаптера, 144 тензора, **1 769 472
  параметров**. Входы: замороженные признаки VTP. Спецификация форм: `protocol/specs/multivsr_lora_r16.json`
  (сгенерирована из кода lipread на устройстве `meta`, без весов).
- Сервис слушает **только localhost**; `server.run` отказывается стартовать на любом другом адресе, переопределения нет.
  Развёртывания этого сервера нет. Для участников из интернета работает другая связка, «Помочь обучить»: приём
  обновлений на Cloudflare Worker, агрегация в GitHub Actions, входящие обновления и публичная модель на Hugging Face
  (раздел 15).

## 3. Что покидает устройство

Тело запроса `POST /v1/updates` состоит ровно из двух частей.

**1. Нагрузка:** файл safetensors с дельтой LoRA (обученный адаптер минус глобальный, **fp16**, 144 тензора). Без
metadata. Размер для MultiVSR: **3,554 МБ** (измерено).

**2. Подписанный манифест** (`SignedManifest`, 528 Б). Схема строгая (`extra=forbid`): любое лишнее поле отвергается.

| Поле | Зачем |
|---|---|
| `client_id` | псевдоним установки (первые 16 байт SHA-256 от публичного ключа), нужен для лимитов и «одно обновление на раунд» |
| `public_key` | Ed25519 публичный ключ установки, проверка подписи |
| `base_version` | версия глобального адаптера, от которой посчитана дельта |
| `num_examples` | сколько примеров участвовало (вес при усреднении; на сервере ограничивается сверху) |
| `schema_version`, `spec_id`, `spec_hash` | служебные: версия формата, какая спецификация адаптера |
| `payload_sha256`, `payload_bytes`, `payload_dtype` | целостность нагрузки |
| `signature` | подпись Ed25519 над каноническим JSON манифеста (покрывает и нагрузку через хэш) |

Не отправляется: видео, кадры, признаки VTP, тексты и расшифровки, названия приложений, имена файлов, имя
пользователя, модель Mac, версия ОС, время отправки (его нет в манифесте; сервер сам фиксирует время приёма).
Каждая отправка записывается локально в `~/.velikiy-moguchiy-federated/upload-log.jsonl` (манифест целиком), чтобы
пользователь мог проверить, что именно ушло.

**Чего это не гарантирует.** Дельта весов не анонимна и не «безопасна по
построению»: адаптер, обученный на нескольких сотнях фраз одного человека, может частично запоминать редкие
фразы, а по обновлениям возможны атаки восстановления данных и определения участия. Сервер видит каждое обновление
по отдельности (безопасной агрегации нет, раздел 14). Сетевая инфраструктура видит IP-адрес. `client_id` постоянен и
позволяет связать обновления одной установки между раундами. Центральный DP (раздел 7) защищает **опубликованный**
глобальный адаптер, но не то, что видит оператор сервера до агрегации.

## 4. Протокол

### 4.1 Ключи и подпись
- Пара Ed25519 создаётся при первом запуске (`Identity.load_or_create`), приватный ключ хранится в
  `~/.velikiy-moguchiy-federated/identity.key` с правами 0600 и не покидает устройство. В планах — хранить его в Keychain вместо файла.
- Подписываются байты `b"velikiy-moguchiy-fl/update/v2\n" + canonical_json(manifest)`; описание глобального адаптера
  сервер подписывает с префиксом `b"velikiy-moguchiy-fl/model/v2\n"`. Префикс домена не даёт использовать подпись в
  другом контексте. Версия протокола 2 (`PROTOCOL_VERSION`, `schema_version` манифеста). Пути HTTP (`/v1/...`) — версия
  REST-интерфейса, они не менялись.
- Сервер проверяет, что `client_id` равен хэшу `public_key` (самосертифицируемый идентификатор), затем подпись.

### 4.2 Конечные точки
| Метод и путь | Назначение |
|---|---|
| `POST /v1/updates` (multipart: `manifest`, `payload`) | приём обновления |
| `GET /v1/model/latest` | описание текущей версии (`ModelInfo`, подписано ключом сервера) |
| `GET /v1/model/{version}/adapter` | файл адаптера (safetensors fp32, 7,093 МБ для MultiVSR) |
| `GET /v1/health` | жив ли сервис, текущая версия |

Порядок проверок в `POST /v1/updates` (первое сработавшее отвергает): `Content-Length` обязателен и не больше
`предел_нагрузки + 8 КБ + 16 КБ` (413/411, до чтения тела) → размер нагрузки → схема манифеста (422) → соответствие ключа и
`client_id` и подпись (401) → SHA-256 и размер нагрузки → спецификация → имена, формы и dtype тензоров, конечность
значений (NaN/Inf) → клиент не заблокирован (403) → **повтор** того же обновления: идемпотентный ответ 200
`duplicate`, даже если база уже устарела → **устаревшая или неизвестная база** (409) → **лимит на установку** (429
с `Retry-After`) → **норма выше порога приёма** (422 `norm_too_large`) → запись.

Коды ошибок (`protocol/errors.py`): `bad_schema 422`, `bad_signature 401`, `bad_payload 422`, `spec_mismatch 422`,
`too_large 413`, `length_required 411`, `nonfinite 422`, `norm_too_large 422`, `stale_base 409`, `unknown_base 409`,
`conflict 409`, `rate_limited 429`, `banned 403`. Клиент повторяет только сетевые сбои, 5xx и 429 с коротким
`Retry-After`; остальное считает окончательным.

### 4.3 Схемы
Pydantic-модели в `protocol/schema.py`; JSON Schema экспортируются в `protocol/schemas/*.json`
(`python -m protocol.schema`).

## 5. Жизненный цикл раунда

Раунд привязан к версии глобального адаптера: «раунд на базе vN» открыт, пока vN текущая.

1. **Раздача.** Клиент скачивает текущую версию vN (проверка подписи, хэша, форм), если ещё нет.
2. **Локальное обучение.** `steps` шагов LoRA на данных пользователя, старт с vN. Выход: локальный адаптер.
3. **Дельта и отправка.** `delta = local − vN`, fp16, подпись, `POST /v1/updates`. На каждую установку принимается не
   более одного обновления на базовую версию.
4. **Накопление.** Принятые обновления лежат со статусом `pending`.
5. **Агрегация** (`python -m server.aggregate`, по расписанию или вручную). Запускается, если ожидающих на текущую
   версию не меньше `min_clients` (по умолчанию 10; `--force` обходит, `--dry-run` только считает).
   Клиппинг → взвешенное усечённое среднее → (опционально DP-шум) → `v(N+1) = vN + server_lr · агрегат`.
   Публикация одной транзакцией SQLite (версия, раунд, смена статусов, указатель на текущую версию), версия
   подписывается ключом сервера.
6. **Закрытие раунда.** Обновления на vN получают статус `aggregated`, файлы дельт удаляются (при
   `retain_payload_days = 0`). Дальнейшие обновления на базе vN отвергаются как `stale_base`.
7. **Следующий раунд** на v(N+1).

Раунд не запускается при `n < min_clients` и без `--force`; обновления остаются ждать. Если за долгое время набрать
`min_clients` не удаётся, оператор решает: снизить порог, дождаться, откатиться. Автоматического снижения порога нет
намеренно (маленький раунд хуже защищён от отравления и от утечек).

Примечание про устаревание: клиент обучается минуты–часы, раунд на сервере может закрыться раньше. Тогда отправка
получит `stale_base`, результат отбрасывается, клиент берёт новую версию и участвует в следующем раунде. Длина
раунда на сервере должна заметно превышать время обучения (сутки и больше).

## 6. Робастность

| Защита | Где | Что делает |
|---|---|---|
| Предел размера | приём | `Content-Length` и размер нагрузки не больше `2·параметры + 64 КБ` |
| Строгая проверка формы | приём | имена, формы, dtype; NaN/Inf отвергаются |
| Подпись и привязка ключа | приём | подделка и подмена манифеста/нагрузки невозможны без приватного ключа установки |
| Порог нормы | приём | `‖Δ‖₂ > limits.max_update_norm` → 422; событие пишется для разбора |
| Устаревшая база | приём | `base_version ≠ текущей` → 409, клиент синхронизируется заново |
| Лимит на установку | приём | `max_updates_per_client_per_day` (по умолчанию 4) попыток с верной подписью за 24 ч, 429 + `Retry-After`; хранится в SQLite |
| Лимит на адрес | приём | `ip_requests_per_minute`, только в памяти, адреса на диск не пишутся |
| Клиппинг по L2 | агрегатор | вся дельта (все тензоры) масштабируется до нормы ≤ C. C фиксированная (`clip_norm > 0`) или адаптивная `C = clip_median_mult · медиана(норм раунда)`, по умолчанию 1,5 |
| Усечённое среднее по координатам | агрегатор | на каждой координате отбрасывается по `k = ⌊trim_ratio · n⌋` наименьших и наибольших значений (по умолчанию 10%), остальные усредняются с весами; всегда остаётся хотя бы один клиент |
| Медиана | агрегатор | `method = "median"`: взвешенная медиана по координатам |
| Ограничение веса | агрегатор | вес клиента `min(num_examples, max_weight_examples)`: заявленное число примеров не проверяется, поэтому влияние ограничено |
| Блокировка | админ | `ban CLIENT_ID` |

В отчёте раунда (`admin rounds`) для каждого клиента сохраняются: норма, множитель клиппинга, доля координат, где
клиент был отброшен. Ожидаемая доля у честного клиента `2k/n`; у отравителя она близка к 1.

**Границы защиты (честно).**
- **Sybil.** Ключ установки бесплатен, злоумышленник может создать сколько угодно «установок». Лимиты на установку
  это не останавливают. Усечённое среднее держит до доли `trim_ratio` отравителей на раунд; больше — не держит.
  Реальная защита — аттестация устройства/приложения (Apple App Attest / DeviceCheck) при выходе наружу *(план)*.
- **Скрытое отравление в пределах нормы.** Обновление с нормой не выше C и «правильным» направлением на большинстве
  координат пройдёт. Поэтому: небольшие раунды опасны, `server_lr < 1` смягчает, а перед публикацией версии нужна
  проверка качества на отложенном наборе (пока вручную через `rollback`; автоматический гейт — *план*).
- **Агрегация факторов LoRA.** Усредняются A и B по отдельности, а не их произведение: `mean(B)·mean(A) ≠ mean(B·A)`.
  Поскольку все стартуют от одной версии и шаги малы, ошибка второго порядка. Точный вариант FFA-LoRA: заморозить A
  (`trainable=false` у тензоров `*.A` в спецификации), слать только B; тогда `mean(B)·A = mean(B·A)` и дельта вдвое меньше.
  Поддержка есть в спецификации и протоколе; решение «замораживать или нет» — после первых реальных запусков.

## 7. Центральная дифференциальная приватность (необязательно, выключено)

Включается `[dp] enabled = true` на сервере. К агрегированной дельте добавляется гауссов шум с
`σ = z · C · w_max / W` на координату (`z` — `noise_multiplier`, `C` — норма клиппинга, `w_max` — наибольший вес,
`W` — сумма весов). Ручки:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `dp.enabled` | `false` | включить |
| `dp.noise_multiplier` | 1.0 | `z`; больше — сильнее приватность, хуже качество |
| `dp.delta` | 1e-6 | δ в (ε, δ) |
| `dp.max_epsilon` | 0 (без лимита) | после превышения накопленного ε новые версии **не публикуются** (код 4) |
| `aggregation.clip_norm` | обязателен > 0 | чувствительность не должна зависеть от данных, поэтому адаптивная C с DP запрещена |

Учёт: RDP гауссова механизма, `ε(α) = α/(2z²)` за раунд, суммируется, перевод
`ε = S/2 + √(2 S ln(1/δ))`, где `S = Σ 1/z²`. Оценка консервативна: один клиент участвует во всех раундах, усиления
от подвыборки нет. Накопленное ε пишется в отчёт раунда и в `admin rounds`.

**Оговорка.** Формальная гарантия верна для `method = "mean"` с фиксированной C. Для усечённого среднего и медианы
чувствительность иная, шум калибруется так же, и ε становится номинальной оценкой (в отчёте помечается
`dp_formal=false`). Это защита опубликованной модели, а не оператора сервера, который видит отдельные обновления.

## 8. Защищённый транспорт

- Только HTTPS. `http://` клиент принимает лишь для localhost при явном `allow_insecure_localhost` (разработка).
- **Закрепление ключа сервера (SPKI pinning)** (есть тест на настоящем TLS): при каждом рукопожатии клиент
  считает SHA-256 от SubjectPublicKeyInfo сертификата и сравнивает с `tls_spki_sha256` из конфигурации **до отправки
  первого байта запроса**. Несовпадение: соединение закрыто, без повторов, ошибка наружу. Проверка цепочки сертификатов
  при этом остаётся (`tls_ca_file` или системные корни) — закрепление это дополнительное условие.
- Минимум TLS 1.2. Прокси из окружения не используются (`trust_env=False`).
- Второй независимый слой: **подпись глобального адаптера** ключом сервера (раздел 10), её публичный ключ тоже
  закреплён (`signing_public_key`). Подмена модели невозможна даже при компрометации TLS.
- Ротация закреплённого ключа: клиент должен получить новый ключ вместе с обновлением приложения; на переходный период
  можно держать в конфигурации два значения *(план)*.
- В симуляции сервер работает по HTTPS с самоподписанным сертификатом и закреплением (`sim/tls.py`).

## 9. Версионирование и откат

- Версии целочисленные и монотонные; каждая подписана (`ModelInfo`: версия, spec_hash, SHA-256 файла, размер, время,
  число клиентов раунда, `rollback_of`).
- **Откат** (`admin rollback --to N`) публикует **новую** версию (N_max+1) с содержимым версии N и
  `rollback_of = N`; версии после N получают статус `revoked` (их скачивание → 404), раунды помечаются
  `rolled_back`, ожидающие обновления на отозванных базах отбрасываются. Номера не переиспользуются, поэтому клиенты
  всегда движутся вперёд, а старая подписанная копия, подставленная злоумышленником, отвергается как понижение версии.
- Клиент хранит текущую и предыдущую версии (`adapters/`), умеет локальный откат (`AdapterStore.rollback_local`).
  Необязательный локальный `validator(path) -> bool` (например, качество на своём dev-наборе) может отказаться ставить
  версию; такая версия запоминается и повторно не качается. В этом раунде клиент не участвует (база не совпала бы).
- Реестр и подписи: SQLite (`versions`, `rounds`) + файлы `versions/vNNNNNN.safetensors`. Отчёты раундов хранят нормы,
  множители клиппинга, долю отброшенных координат.

## 10. Как глобальный адаптер возвращается клиентам

1. Агрегатор публикует версию; сервер отдаёт `GET /v1/model/latest` с подписанным `ModelInfo`.
2. Клиент при каждом проходе (после проверки условий планировщика) запрашивает `latest`, проверяет подпись
   закреплённым ключом, `spec_hash`, что версия не ниже установленной, размер не выше ожидаемого.
3. Скачивает файл, проверяет размер и SHA-256 из подписанного описания, имена/формы/dtype/конечность.
4. Устанавливает атомарно (`.tmp` → rename), сдвигает `current/previous`.
5. Приложение читает установленный адаптер и подмешивает в инференс (слияние `W += (α/r)·B·A`, как делает
   `lora.merge_lora_into_base`) при следующем запуске распознавания. Этот шаг — план: в приложение он ещё не встроен.

Адаптер публичен для всех установок (он не личный), поэтому его можно раздавать статикой/CDN; `ETag` равен SHA-256.
Клиент всё равно доверяет только подписи.

Размеры на раунд (MultiVSR, измерено): вверх 3,554 МБ, вниз 7,093 МБ.

## 11. Планировщик и охранник памяти на машине пользователя

Условия запуска (все сразу, `client/scheduler.py`): питание от сети (`pmset -g batt`: «AC Power»), режим
энергосбережения выключен (`pmset -g`: `lowpowermode`/`powermode`), Mac не используется не менее `idle_minutes`
(`ioreg -c IOHIDSystem`, `HIDIdleTime` в наносекундах; если определить простой не удалось, считается, что
пользователь на месте), прошло `min_hours_between_runs` с прошлого участия. Бюджет `max_runtime_minutes` ограничивает
**активное** время обучения.

Во время обучения условия пере-проверяются каждые `monitor_seconds`: вернулись к Mac или отключили зарядку →
остановка. Прерванное обучение отправляется, если сделано не меньше `min_steps_fraction` шагов (по умолчанию 50%),
иначе результат отбрасывается.

**Охранник памяти (обязательно для локального тренера).** На машинах пользователей тренер всегда запускается под
`mem_guard.py` (в клиенте лежит копия `client/vendor/mem_guard.py` из `tools/` в корне репозитория, потому что в
собранном приложении каталога `tools/` не будет; чем она отличается от оригинала — в `client/vendor/README.md`). Охранник: бюджет памяти = доступная память минус резерв
(`guard.reserve_gb`, по умолчанию 6 ГБ) → лимиты MPS; при росте свопа больше `max_swap_growth_mb` или падении свободной
памяти ниже `min_free_pct` ставит **всю группу процессов тренера на паузу (SIGSTOP)**, при восстановлении
возобновляет (SIGCONT). Следствия для клиента:

1. **Тренер переживает паузы.** Бюджет времени считается по активному времени (`ActiveClock`): для подпроцесса пауза
   видна по состоянию процессов группы (`T` в `ps`, `GroupPauseProbe`), для обучения внутри процесса — по скачку
   времени между проверками. Паузы не съедают бюджет и не считаются зависанием.
2. **Нет сети во время обучения.** Сначала обучение, потом упаковка и отправка; остановленный процесс не оставляет
   полуоткрытых соединений. Планировщик и сетевая часть остаются в отдельном (не замораживаемом) процессе.
3. **Остановка** делается SIGINT охранника: он снимает паузу и посылает группе тренера SIGTERM (train.py при этом
   сохраняет контрольную точку), через 120 с — SIGKILL.
4. **Один процесс модели за раз:** демон не запускает второе обучение, пока первое не завершено.
5. Охранник не заменяет условий планировщика: при нехватке памяти обучение ждёт, а не отменяется; отменяется оно
   только при возвращении пользователя, отключении питания или исчерпании активного бюджета.

(Проверено: в одном из прогонов симуляции охранник трижды ставил процесс на паузу из-за роста свопа от других
программ, прогон дошёл до конца с теми же числами.)

## 12. Режимы отказов

| Ситуация | Поведение |
|---|---|
| Сервер недоступен | повторы с экспоненциальной задержкой (5 с … 300 с, джиттер) до `retry_attempts`; затем обновление остаётся в `outbox/` и уходит на следующем проходе, если база ещё актуальна |
| Ответ потерян, клиент повторил | сервер идемпотентен: `duplicate`, второй записи нет |
| База устарела (`stale_base`) | результат отбрасывается, outbox очищается, следующая синхронизация берёт новую версию |
| Лимит 429 | при `Retry-After` до 300 с ждём, больше — прекращаем попытку, повторим на следующем проходе |
| Подпись/схема/форма не прошла (4xx) | окончательно, outbox очищается (повтор бесполезен); пользователю ничего не показывается, запись в `upload-log.jsonl` |
| Мало клиентов в раунде | версия не публикуется, обновления ждут; решение оператора |
| Подпись модели/хэш/форма не сошлись | адаптер не устанавливается, остаётся предыдущий |
| Версия ниже установленной | отвергается (защита от подмены старым ответом) |
| Закреплённый ключ TLS не совпал | соединение отвергнуто без повторов и без отправки тела |
| Плохая версия попала в реестр | `admin rollback --to N`; клиенты получают новую версию-копию; локально `rollback_local` |
| Падение агрегатора посреди раунда | публикация одной транзакцией: версия не появляется наполовину; обновления остаются `pending` |
| Параллельный откат во время агрегации | агрегатор сверяет текущую версию внутри транзакции и отменяет раунд |
| Нехватка памяти / своп на Mac | охранник ставит тренер на паузу (раздел 11) |
| Пользователь вернулся / отключили зарядку | тренер останавливается, результат отправляется при ≥50% шагов |
| Диск заполнен | запись outbox/адаптера падает с ошибкой, проход завершается `error`, следующий проход повторит |
| Дрейф данных/деградация модели | вне протокола: гейт качества перед публикацией *(план)*, откат |

## 13. Масштаб

Агрегатор держит в памяти векторы клиентов раунда (7 МБ fp32 на клиента для MultiVSR) и считает по кускам
координат. Для сотен клиентов в раунде это ещё гигабайты; для тысяч нужна потоковая/иерархическая агрегация *(план)*.
Сервер приёма синхронный и однопроцессный: достаточно для одного Mac-хоста; горизонтальное масштабирование (общая БД
вместо SQLite) вне текущей задачи.

## 14. Привязка к будущему расположению

Ниже — как каркас из этой папки ложится на приложение и на собственный сервер. Серверная часть таблицы описывает
развёртывание кода из `server/` на своём хосте; для «Помочь обучить» вместо него работает связка с Cloudflare Worker,
GitHub Actions и Hugging Face (раздел 15).

Стиль: как уже существующий вспомогательный `mic-warm` — отдельный исполняемый файл в бандле `VelikiyMoguchiy.app`
(`Contents/MacOS/`), который приложение запускает через `NSTask` (`SPAppDelegate.m`: `startMicWarmIfEnabled`,
`--parent-pid`, остановка SIGTERM → SIGKILL) и который сам завершается, когда исчезает родительский процесс.

| Компонент | Где будет жить | Как запускается |
|---|---|---|
| Клиентский демон (`client.runner daemon`) | Python-сервис в бандле приложения (рядом с `velikiy-moguchiy-cli`, `mic-warm`), собирается в `Makefile` (`install-cli`) | `NSTask` при старте приложения, флаг `--parent-pid` уже поддержан; включение по ключу конфигурации (как `experimental.keep_mic_warm`) |
| Тренер | подпроцесс клиента: окружение lipread (venv с PyTorch) + `train.py` | запускается демоном под `mem_guard.py`; копия охранника уже в `client/vendor/` |
| Идентификатор/ключи | `~/.velikiy-moguchiy-federated/identity.key` | позже Keychain |
| Конфигурация | `~/.velikiy-moguchiy-federated/config.toml` | по умолчанию пишет `client.runner init`; ключ подписи сервера и закрепление TLS вшиваются в приложение |
| Загруженный адаптер | `~/.velikiy-moguchiy-federated/adapters/` | читается при инициализации распознавателя |
| Сервер, агрегатор, админ-CLI | отдельный хост оператора; здесь только локальный запуск | `python -m server.run`, cron/launchd для `python -m server.aggregate`; при выходе наружу — за обратным прокси с TLS, с мониторингом и резервными копиями SQLite |
| Ключ подписи моделей | `server_data/keys/model_signing.key` | при выходе наружу — хранить офлайн или в HSM, на сервере только подписание |

Что нужно решить при выходе наружу: аттестация устройств (Sybil), безопасная агрегация (чтобы оператор не видел
отдельные обновления), хост и TLS-сертификат, гейт качества перед публикацией версии, ротация ключей.

## 15. Выход наружу: «Помочь обучить» на Hugging Face и GitHub Actions

Решения из раздела 14 для Cloudflare Workers, Hugging Face и GitHub Actions. Код: `worker/`, `hub/`, `aggregator/`, `client/community.py`;
шаги владельца: `../../docs/AUTOMATION.md`, устройство: `docs/DEPLOY.md`.

- **Данные.** Участник учится не на своих записях, а на публичных роликах из задания: сервер выдаёт id роликов и
  отрезки с расшифровкой (пул собран из открытых метаданных датасета MultiVSR и лежит в закрытом датасете, в git его
  нет), участник качает только видеодорожку со своего адреса, режет и обучает у себя. Каналы из журнала исключений
  `data-governance/` не попадают в пул, а у роликов без известного канала клиент узнаёт его у yt-dlp и пропускает
  исключённые; без журнала задание не идёт. Личные папки приложения задание не трогает (`client/privacy.py`).
- **Личность и Sybil.** Логин GitHub по токену без прав; аккаунт моложе 30 дней не принимается; лимиты на логин
  (заданий и обновлений за сутки, одно обновление на версию) хранятся в KV сервера приёма (у Python-варианта
  считаются ещё и по сохранённым обновлениям). Ключ установки по-прежнему подписывает манифест (протокол v2).
- **Что принимает сервер.** Ровно три части: подписанный манифест, дельта в safetensors (pickle, zip `torch.save`,
  numpy и всё, что не начинается с JSON-заголовка safetensors, отвергается по сигнатуре до разбора), подписанные
  сведения о вкладе (`protocol/contribution.py`: секунды, шаги, число отрезков, токен задания). Токен задания
  подписан HMAC сервера: засчитывается не больше секунд и шагов, чем было в задании.
- **Хранение.** Сервер приёма (Cloudflare Worker; запасной — Space) без состояния, кроме лимитов: входящие — закрытый датасет (`pending/<логин>/...`, удаляются агрегатором),
  версии — открытый репозиторий модели (`index.json` с подписанными `ModelInfo`, все версии хранятся).
- **Изоляция ключа.** Оценка с кодом MultiVSR идёт в отдельном задании без секретов; публикация на другом раннере,
  без torch, сама пересобирает слияние из заново проверенных обновлений и подписывает его, только если хэш совпал с
  оценённым. Слияние требует не меньше 5 принятых обновлений, вес обновления ограничен числом отрезков его задания.
- **Гейт качества и откат.** Агрегатор (раз в сутки, CPU бесплатного раннера) считает WER базы и базы + каждого
  обновления на скрытом экзамене: публичные клипы MuAViC-ru, которых нет в пуле; признаки VTP задание оценки
  считает само, без секретов (`aggregator/exam_features.py`), вливается только LoRA. Записи автора проекта в экзамен
  не входят. Ухудшающее отклоняется; принятые
  клиппируются и усредняются с обрезкой; слияние, которое хуже базы, не публикуется (текущей остаётся прежняя
  версия). Опубликованный файл сверяется с проверенным; при расхождении сразу публикуется откат (новая версия с
  содержимым прежней, остальные отозваны). Ручной откат — тот же процесс с номером версии.
- **Ключи.** Закрытый ключ подписи моделей только в секрете GitHub Actions; открытый вшит в приложение
  (`client/community_defaults.py`, пишет деплой). TLS сервера приёма не закрепляется (сертификаты меняет хостинг), а версии адаптера клиент берёт прямо из открытого репозитория модели:
  подлинность модели держится на подписи.
- **Вклад.** Принятые обновления опубликованной версии дают строки в `contributors.json` (логин, часы, шаги,
  принятые обновления), коммит делает github-actions; можно отказаться от показа логина (`credit_public = false`).
- **Не решено.** Безопасная агрегация (оператор видит отдельные обновления), формальная DP для усечённого
  среднего, «тихое» отравление в пределах нормы и без ухудшения экзамена, приватность IP участника перед YouTube.
